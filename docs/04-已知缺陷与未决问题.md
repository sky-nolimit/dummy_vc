## A. 会影响结果正确性的

### A1. URDF 的夹爪模型与实物不符 ★

| | |
|---|---|
| **现象** | URDF 里的夹爪是原作者模型:`dummy_hand_v1_1` 一块平板掌 + 两个细长棱柱手指,prismatic 行程各 **0.023 m**,两指沿 ±x 对开 |
| **实物** | 舵机 + **齿轮齿条** + **两条直线导轨** + 两个**白色打印长手指**装在黑色滑块上,掌部是一整块黑色机构盒 |
| **证据** | 实物照片(2026-10-14);URDF `dummy2_urdf.xacro` L188–L228、L360–L374 |
| **影响** | ① RViz 里夹爪外形是错的 ② `gripper_tcp` 是**占位值**,不代表真实抓取中心 ③ MoveIt 用的是错的末端几何 ④ 视觉算出的抓取点会和实际差 **几十毫米** —— 足以让"抓住"变成"推倒" |
| **需要什么** | 实测:两指实际开口范围、手指长度与形状、抓取中心相对 `link7_v1_1` 的偏移、导轨行程。**然后重建 link/关节**(或换一个匹配的夹爪 URDF) |
| **注意** | 改夹爪几何会**同时**影响:`gripper_tcp`、SRDF 里 `gripper` 组的关节名与行程、`joint_limits`、以及视觉的抓取点定义。**要一起改,不能只改 mesh** |

### A2. 夹爪不可驱动

| | |
|---|---|
| **现象** | `robot.hand` 的三个方法 `set_angle` / `set_enable` / `set_current_limit` **全部永久阻塞**,任何命令都不产生动作 |
| **证据** | 多轮实测(不同调用顺序、不同供电状态,结果一致);协议转储显示夹爪占 **endpoint id 296~301**;`gripper_ids.py` 全协议搜索确认 **`hand` 是唯一通路** |
| **机制** | 客户端 `fibre/remote_object.py` 的 `set_value` / `__call__` 都用 `expect_response=True` **且无超时**;`robot.move_j` 走同一代码路径却能返回 → **固件不响应这些 id** |
| **已排除** | 舵机没供电(整机使能后手指变硬、有力矩)、调用顺序(`--prime` 复刻驱动顺序仍全挂)、协议声明形式(与 `move_j` 结构相同)、线缆断开或插座空置(用户目视确认) |
| **接线** | 夹爪信号从 **j6 的驱动板**引出 |
| **影响** | **抓取的最后一步做不了。** 但视觉、定位、规划、移动到位都不需要它 |
| **需要什么** | 厂商固件修复;或**直接对 CAN 总线说话**(见下面的补充) |
| **不要做** | 不要在 `moveit_controllers.yaml` 里给夹爪注册控制器 —— 会让 MoveIt 以为能夹,规划里带闭合动作就挂在一个永不返回的调用上 |

#### A2-补充:夹爪的真实接口(来自作者分享的固件源码)

**2026-10-14 拿到作者分享的固件源码**(`2.Firmware/Dummy 源码注释/`),
`DummyHand` 的实现把夹爪的真相讲清楚了。**此前所有关于量纲的猜测都作废。**

```cpp
// dummy_robot.h
uint8_t nodeID = 7;          // CAN 节点号
float   maxCurrent = 0.7;    // 默认最大电流

// dummy_robot.cpp
DummyHand::SetAngle(float _angle) {
    if (_angle > 30) _angle = 30;      // ★ 范围 0..30，不是 0..90
    if (_angle < 0)  _angle = 0;
    uint8_t mode = 0x02;               // ★ 角度 mode = 0x02
    txHeader.StdId = 7 << 7 | mode;    // 扩展帧，节点 7
    /* 4 字节 float 小端写入 canBuf */
    CanSendMessage(get_can_ctx(hcan), canBuf, &txHeader);
}

DummyHand::SetMaxCurrent(float _val) {
    if (_val > 1) _val = 1;            // ★ 范围 0..1
    if (_val < 0) _val = 0;
    uint8_t mode = 0x01;               // ★ 电流 mode = 0x01
    txHeader.StdId = 7 << 7 | mode;
    CanSendMessage(...);
}

DummyHand::SetEnable(bool _enable) {
    if (_enable) SetMaxCurrent(maxCurrent);   // ★ 不是独立命令
    else         SetMaxCurrent(0);
}
```

**由此确定的四件事:**

| 项 | 实际值 | 我们此前的假设 |
|---|---|---|
| 角度范围 | **0 ~ 30** | 以为 0~90(`grip_angle_open` 写的是 90) |
| 电流范围 | **0 ~ 1.0**,固件默认 **0.7** | 我们默认 0.1(偏保守,不算错) |
| `set_enable` | **只是写电流上限**,不是独立命令 | 以为是一条独立指令 |
| 通信 | **CAN 扩展帧,节点 7** | 未知 |

**`set_angle(90)` 在固件里会被夹到 30。** 我们之前"试 90 度"其实等于试 30 度。
这不是没反应的原因,但说明我们一直在拿超出范围的数去试。

**更重要的一点:`set_enable` 只是写电流上限,它本身没有理由阻塞。**
而 `CanSendMessage` 在电机和夹爪上是**同一个函数**(`ctrl_step.cpp` 与
`dummy_robot.cpp` 都调它),电机命令一直正常 —— **所以 CAN 总线是通的。**

阻塞只能发生在**固件处理 hand 这几个 endpoint 的那一层**,不在 CAN 发送本身。
**范围缩小了,但仍需厂商修复或直接对 CAN 说话。**

**一条可行的绕过路径:** 舵机是**总线舵机**(CAN 节点 7)。若能让上位机直接
访问那条 CAN 总线,就可以自己发 `StdId = (7<<7)|0x02` + 4 字节 float,
**完全绕开 fibre 和主控固件**。需要先确认 CAN 总线是否对外可达。

**⚠ 动手前先处理 A1** —— 夹爪几何与实物不符,而重建几何和接通驱动动的是
同一批文件。

## B. 会影响可观测性的

### B1. `/joint_states` 滞后于实际运动

| | |
|---|---|
| **现象** | 手动测试 `final_test.py` 时,脚本输出已经翻到 j3,机械臂还在跑 j2 |
| **证据** | 用户观察(2026-10-13) |
| **已排除** | 固定等待太短 —— 等待逻辑已改为"先等起步、再等停止",且 `selftest_wait.py` 对模拟慢速设备四例全过 |
| **推测** | 驱动发布的角度由设备回读换算而来;若轮询落后于命令,已发布的角度会在手臂实际开动**之后**才变化。任何观察 `/joint_states` 的东西都会看到运动"晚开始" |
| **影响** | `final_test.py` 的第 3、4 项 **FAIL 不可采信**(已在文件顶部标注);RViz 里模型跟随有延迟 |
| **需要什么** | 测量"下发命令到 `/joint_states` 反映变化"的实际延迟;确认是轮询周期问题还是设备回读本身滞后 |

### B2. 夹爪没有回读

| | |
|---|---|
| **现象** | `hand` 上只有三个 `set_*` 方法,**零个可读属性** |
| **证据** | `probe_gripper.py --stage 0` 实测(`set_* methods (3)`, `everything else (0)`, `hand.angle exists: False`) |
| **影响** | ① `/joint_states` 里的手指位置是**最近命令值**,不是测量值 —— 夹住东西时模型仍显示合拢到位 ② 夹持力无法闭环 |
| **已处理** | 驱动原先用 `getattr(hand, 'angle', 0.0)`,会**永远静默返回 0 且不报错**;已改为跟踪命令值并在启动时明确 warn |
| **需要什么** | 若将来换总线舵机(有位置反馈),可以把回读加回来 |

## C. 精度与标定上的

### C1. 关节符号的 j1/j4/j5/j6 缺独立证据

| | |
|---|---|
| **现象** | 只有 j2/j3 的符号有独立验证(几何折叠 + 实测命令) |
| **原因** | 两个参考姿态(home/reset)之间 j1/j4/j5/j6 几乎不动,判定不了符号 |
| **影响** | 目前它们能动、方向与预期一致(手动测试观察),但**没有第二份证据** |
| **需要什么** | 找一个能明显转动这四个关节的姿态对,做同样的"几何 + 实测命令"校验 |

### C2. move_j 可接受区间是 15 度步长扫出来的

| | |
|---|---|
| **现象** | `probe_range.py` 用 15 度网格,所以边界精度是 ±15 度 |
| **证据** | 各关节实测区间与 URDF 限位吻合到 ±15 度,正是网格宽度 |
| **影响** | 区间边界附近可能有几度的值实际可用却被拒绝(或反之) |
| **需要什么** | 若要精确边界,在边界附近用小步长(2~5 度)重扫 |

### C3. 夹爪的电流上限从未标定,默认值只求安全

| | |
|---|---|
| **现象** | `grip_current_limit` 从 1.0 降到 **0.1**,只是"第一次上电不会压坏东西"的量级 |
| **原因** | 没有力/电流回读,方案里"扫出夹稳不碎区间"的做法**做不到** |
| **影响** | 将来真能驱动夹爪时,这个值必须实测重定 |
| **需要什么** | 能观测到夹爪状态之后(位置或电流),用纸杯/鸡蛋这类不心疼的东西扫 |

## F. 由固件源码产生的新问题

**2026-10-14 拿到作者分享的固件源码**，完整对照见
[05-固件源码事实.md](05-固件源码事实.md)。它同时产生了两个待查项。

### F1. 设备上跑的固件是不是这份源码编译的？

| | |
|---|---|
| **为什么要问** | 源码里 `hand` 的实现只是发一帧 CAN、**没有任何等待**，所以 `set_enable` / `set_angle` 不该阻塞。而实测三个都永久阻塞 |
| **含义** | 若设备运行的固件版本与这份源码**不同**，`hand` 阻塞的解释可能就在版本差异里 —— 这比继续从行为反推更有价值 |
| **怎么查** | 找固件的版本号或编译日期；或问作者这份源码对应哪个固件版本 |

### F2. `绝对角度 = initPose + move_j`，为什么与实测的 move_j 区间对不上？

| | |
|---|---|
| **源码** | `MoveJ` 检查**绝对角度**是否在 `motorJ[j]` 的限位内；`MoveJoints` 下发的是 `目标 − initPose`，即 `绝对 = initPose + move_j` |
| **若 initPose = (0,0,90,0,0,0)** | j3 的绝对角度 `= move_j_j3 + 90`，必须落在固件的 `[35, 180]` → `move_j_j3 ∈ [-55, 90]` |
| **实测** | j3 的可接受区间是 **[45, 180]** |
| **矛盾** | 两者只在 `[45, 90]` 重叠，**下界不同**。所以要么 `initPose` 不是 `(0,0,90)`，要么 `move_j` 空间与这套绝对角度之间还差一个偏移 |
| **为什么重要** | `MoveJ` 越界时**静默返回 false**，不报错 —— 这正是"下发成功但不动"的机制。搞清这层映射，就能**预测**哪些目标会被拒绝，而不是靠扫描 |
| **怎么查** | 命令一个已知 `move_j`，同时读固件侧的绝对角度目标，量出两者的关系 |
| **注意** | `MoveJ` 用 `>` / `<` 比较，所以**边界值本身通过** |

### F3. 固件的运动学连杆参数可能与 URDF 不同

`dummy_robot.cpp` L48：`DOF6Kinematic(0.109, 0.035, 0.146, 0.115, 0.052, 0.072)`。

这是固件做 IK/FK 用的连杆长度，**是独立于 URDF 的另一份几何**。将来核对正运动学
或排查"规划的位置和实际不符"时，这份参数是第三方参照。

### F4. j2 的收缩姿态差 2 度

`REST_POSE = {0, -73, 180, 0, 0, 0}`（相对 `initPose`），而我们的
`reset_joints_deg = [0, -75, 180, 0, 0, 0]`。**不影响功能**，但两个值来源不同，
记下来免得以后当成 bug 查。

## E. 已经解决、留作参考的

这些曾经是问题,现在有检查守着,列出来是为了不再踩。

| 项 | 曾经的后果 | 现在由谁守 |
|---|---|---|
| `[0,360)` 归一化 move_j | 命令被设备静默丢弃 | `normalize_movej` 按区间折叠 |
| 用"回读反推"当前位置 | j3 目标偏 90 度 | 改为命令历史;`check_downlink.py` |
| **下发链常数项错** | **j3 目标 −1.474,超出 `[45,180]` → 整条命令被丢** | `check_downlink.py` 对实测配对,最大偏差 0.007 度 |

| 驱动读 `hand.angle` 静默假报 | RViz 里手指永远不动且无警告 | 改为跟踪命令值 + 启动 warn |
| 控制器名与驱动话题不匹配 | 轨迹发到没人读的话题,MoveIt 报成功而机械臂不动 | `check_moveit_config.py` |
| 读硬件与发话题耦合(20 Hz 单定时器) | RViz 跳变,140 次/秒阻塞 USB | 拆成 10 Hz 读 + 50 Hz 发 |

## 处理顺序的建议

1. **先做不需要夹爪的部分** —— 阶段 2 规划、阶段 4 视觉、手眼标定。这些是项目主体,而且夹爪通不通都不影响。
2. **A1(夹爪几何)与 A2(夹爪驱动)一起处理** —— 两者都动到同一批文件(SRDF 的 `gripper` 组、`gripper_tcp`、视觉抓取点定义),分开做会返工。
3. **B1 可以在做 RViz 相关的事时顺手量掉**,它不影响抓取流程的正确性。
4. **C1/C2 不阻塞任何事**,等有需要时再补。
