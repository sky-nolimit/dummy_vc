## 1. 夹爪（`DummyHand`）—— 这一节推翻了此前的量纲假设

### 1.1 类的定义

`dummy_robot.h`:

```cpp
class DummyHand {
public:
  uint8_t nodeID = 7;         // CAN 节点号
  float   maxCurrent = 0.7;   // 默认最大电流
  DummyHand(CAN_HandleTypeDef* _hcan, uint8_t _id);
  void SetAngle(float _angle);
  void SetMaxCurrent(float _val);
  void SetEnable(bool _enable);
  ...
  make_protocol_function("set_angle",         *this, &DummyHand::SetAngle,        "angle");
  make_protocol_function("set_enable",        *this, &DummyHand::SetEnable,       "enable");
  make_protocol_function("set_current_limit", *this, &DummyHand::SetMaxCurrent,   "current");
```

**协议里的三个函数名与我们看到的 `hand.set_angle / set_enable /
set_current_limit` 一一对应。** 所以接口是对的，问题不在命名。

### 1.2 三个函数的实现

`dummy_robot.cpp`:

```cpp
void DummyHand::SetAngle(float _angle)
{
    if (_angle > 30) _angle = 30;
    if (_angle < 0)  _angle = 0;

    uint8_t mode = 0x02;
    txHeader.StdId = 7 << 7 | mode;

    auto* b = (unsigned char*) &_angle;
    for (int i = 0; i < 4; i++) canBuf[i] = *(b + i);   // float 小端

    CanSendMessage(get_can_ctx(hcan), canBuf, &txHeader);
}

void DummyHand::SetMaxCurrent(float _val)
{
    if (_val > 1) _val = 1;
    if (_val < 0) _val = 0;

    uint8_t mode = 0x01;
    txHeader.StdId = 7 << 7 | mode;
    ... 同样写 4 字节 float ...
    CanSendMessage(get_can_ctx(hcan), canBuf, &txHeader);
}

void DummyHand::SetEnable(bool _enable)
{
    if (_enable) SetMaxCurrent(maxCurrent);   // ★ 不是独立命令
    else         SetMaxCurrent(0);
}
```

### 1.3 由此确定的事实

| 项 | 实际 | 我们此前的假设 | 处置 |
|---|---|---|---|
| 角度范围 | **0 ~ 30** | 0 ~ 90 | 已改 `grip_angle_open: 30.0` |
| 电流范围 | **0 ~ 1.0** | 0 ~ 1.0 | 一致 |
| 电流默认 | 固件 **0.7** | 我们 0.1 | **保留 0.1**：固件那个 0.7 对未标定的夹爪偏大 |
| `set_enable` | **只是 `SetMaxCurrent(maxCurrent)`** | 以为是独立指令 | 见 1.4 |
| 通信 | **CAN 扩展帧，节点 7**，mode 0x02=角度 / 0x01=电流 | 未知 | 见 1.5 |
| 角度单位 | **度**（float） | 度 | 一致 |

**`set_angle(90)` 会被固件夹到 30。** 所以我们之前"试 90"其实等于试 30 ——
不是没反应的原因，但说明一直在拿超范围的数去试。

### 1.4 `set_enable` 阻塞这件事，源码说不通

`SetEnable` 最后落到 `SetMaxCurrent`，只是**发一帧 CAN**，没有任何等待。

而 `CanSendMessage` 在**电机和夹爪上是同一个函数**：

```
ctrl_step.cpp   L35, L49, ... 30 处   CanSendMessage(...)
dummy_robot.cpp L435, L452             CanSendMessage(...)
```

**电机命令一直正常工作 → CAN 总线是通的、这个函数是可用的。**

所以 `hand.set_*` 永久阻塞**只能发生在固件处理这几个 endpoint 的那一层**，
不在 CAN 发送本身。

**还有一个可能，值得先排查：本机跑的固件可能不是这份源码编译的。**
源码里有 `hand`，但设备不一定运行同一版本。**这一条比继续猜更有价值。**

### 1.5 一条可行的绕过路径

舵机是**总线舵机**：CAN 扩展帧，`StdId = (7 << 7) | mode`，
mode `0x02` = 角度、`0x01` = 电流，负载是 4 字节小端 float。

> **若上位机能直接访问那条 CAN 总线，就可以完全绕开 fibre 与主控固件。**

需要先确认 CAN 总线是否对外可达（夹爪信号从 **j6 的驱动板**引出）。

## 2. 关节电机 —— 有一处需要用实测交叉验证

### 2.1 构造函数里的限位

`dummy_robot.cpp` L36–L49:

```cpp
motorJ[ALL] = new CtrlStepMotor(_hcan, 0, false,  1, -180, 180);
motorJ[1]   = new CtrlStepMotor(_hcan, 1, true,  30, -170, 170);
motorJ[2]   = new CtrlStepMotor(_hcan, 2, false, 30,  -73,  90);
motorJ[3]   = new CtrlStepMotor(_hcan, 3, true,  30,   35, 180);
motorJ[4]   = new CtrlStepMotor(_hcan, 4, false, 24, -180, 180);
motorJ[5]   = new CtrlStepMotor(_hcan, 5, true,  30, -120, 120);
motorJ[6]   = new CtrlStepMotor(_hcan, 6, true,  50, -720, 720);
hand        = new DummyHand(_hcan, 7);          // ★ 夹爪是节点 7
```

**签名推断**：`(hcan, nodeID, reversed, reduction, angleLimitMin, angleLimitMax)`。
第 3 个参数 `true/false` 与"方向"相关（1、3、5、6 为 true，2、4 为 false），
`reduction` 是减速比（夹爪那一项没有，因为它不是电机）。

### 2.2 `MoveJ` 会检查限位，越界**静默返回 false**

`dummy_robot.cpp` L95–L132:

```cpp
bool DummyRobot::MoveJ(float _j1, ..., float _j6)
{
    DOF6Kinematic::Joint6D_t targetJointsTmp(_j1, ..., _j6);
    bool valid = true;
    for (int j = 1; j <= 6; j++) {
        if (targetJointsTmp.a[j-1] > motorJ[j]->angleLimitMax ||
            targetJointsTmp.a[j-1] < motorJ[j]->angleLimitMin)
            valid = false;
    }
    if (valid) { ...计算速度、设置 targetJoints...; return true; }
    return false;          // ★ 越界就什么都不做
}
```

**这解释了一个长期现象：设备会静默忽略它不愿执行的目标。**
（通过 USB 命令行时调用者看不到返回值，所以表现为"下发成功但不动"。）

### 2.3 与实测区间的关系：需要交叉验证

固件检查的是**绝对角度** `targetJointsTmp`，而 `MoveJoints` 下发时做的是

```cpp
motorJ[j]->SetAngleWithVelocityLimit(_joints.a[j-1] - initPose.a[j-1], ...);
```

也就是 **`绝对 = initPose + move_j`**。

如果 7 姿态下 `initPose = (0, 0, 90, 0, 0, 0)`（`CalibrateHomeOffset` 里确实
设成这个），那么 j3 有：

```
绝对 j3 = move_j_j3 + 90       必须落在 [35, 180]
=> move_j_j3 必须落在 [-55, 90]
```

**而我们实测 j3 的可接受区间是 [45, 180]。两者不一致。**

这说明要么 `initPose` 不是 `(0,0,90)`，要么 `move_j` 空间与这套绝对角度之间还
差一个偏移。**在改写任何东西之前，应当用一条明确的实验把这个关系量出来**
（例如：命令一个已知的 `move_j`，同时看固件侧的绝对角度目标）。

**注意**：`MoveJ` 的限位检查用的是 `> / <`，所以边界值本身是**通过**的。
我们的实测区间 `[45, 180]` 与 `[-55, 90]` 重叠在 `[45, 90]` —— 一个
**下界不同、上界相同**的形状，值得注意。

### 2.4 两点附注

- `REST_POSE = {0, -73, 180, 0, 0, 0}`（相对 `initPose`），而我们配置里的
  `reset_joints_deg = [0, -75, 180, 0, 0, 0]`。**j2 差 2 度**（−73 vs −75）。
  不影响功能，但说明这两个值来源不同，值得记下。
- 固件里**没有** `hand` 角度的其它常量 —— 0~30 就是完整的范围声明。

## 3. 命令模式

`dummy_robot.h` L90–L98, L164:

```cpp
enum CommandMode {
    COMMAND_TARGET_POINT_SEQUENTIAL   = 1,
    COMMAND_TARGET_POINT_INTERRUPTABLE,
    COMMAND_CONTINUES_TRAJECTORY,
    COMMAND_MOTOR_TUNING
};
const CommandMode DEFAULT_COMMAND_MODE = COMMAND_TARGET_POINT_INTERRUPTABLE;
```

| 模式 | 值 | 行为（`SetCommandMode`） |
|---|---|---|
| SEQUENTIAL | 1 | `jointSpeedRatio = 1`，低加速度；`ParseCommand` 里**执行完等 `IsMoving()` 结束才回 "ok"** |
| INTERRUPTABLE | 2 | **默认**；不等运动结束就回 "ok" |
| CONTINUES_TRAJECTORY | 3 | `jointSpeedRatio = 0.3`，高加速度 |
| MOTOR_TUNING | 4 | 不设置任何东西 |

**默认是 INTERRUPTABLE**，所以 `move_j` 会立刻返回 "ok" 而不等手臂到位。
这与我们观察到的"下发成功但手臂还在走"一致。

## 4. 其他可能有用的事实

| 项 | 值 | 出处 |
