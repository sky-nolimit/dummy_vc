## 为什么必须先做这件事

接口探测已经把「未知的接口」变成了「未知的数值」。这些数值不能用任何方式猜：

- **关节方向与单位**：URDF 里 j1 轴是 `-z`、j5 是 `-x`、j6 是 `-y`；参考项目还额外有一层 `rad_fix`（含 +90° 偏置和 j5/j6 反向）。多层叠加，猜错一层就是系统性镜像，而症状和「标定不准」几乎无法区分。
- **夹爪角度范围**：URDF 标的是手指 prismatic 0~0.023 m，硬件给的是 `hand.angle`，中间没有公开换算。误差 5 mm 就足以让抓取从「抓住」变成「推倒」。
- **夹持力**：`set_current_limit` 是唯一能防夹碎的手段，但安全区间只能试出来。
- **`set_position_with_time(pos, time)` 的单位**：pos 是度还是弧度？time 是秒还是毫秒？决定轨迹执行怎么写。（**pos 已确认是度**）
- **TCP 偏移**：决定 IK 精度。

半天测量，能省掉后面几天的返工。

## 安全设计：预览 → 确认 → 执行

标定节点**不会**在你敲下命令时立刻驱动硬件。

```
你调用 /calib/joint_step          → 节点进入 PREVIEW，把目标姿态发布到
                                    /calib/ghost_joint_states 和 /calib/markers
你在 RViz 里看                     → 确认目标姿态是你要的
你调用 /calib/confirm data=true    → 才真正下发设备
你调用 /calib/confirm data=false   → 取消，ghost 回到实际姿态
```

此外还有三层保护：

| 保护 | 说明 |
|---|---|
| `max_joint_delta`（默认 0.15） | 单步关节增量超限会被自动截断 |
| `max_gripper_delta`（默认 3.0） | 同上，夹爪 |
| `safe_current_limit`（默认 1.0） | **启动时先设这个值**，退出时再设回去，避免大电流被遗留在设备上 |
| `dry_run` 参数 | 置 true 则完全不下发硬件，可先验证节点和 RViz 配置 |

⚠️ **重要：标定节点和 `dummy_controller` 不能同时运行。** 两者都会去抢同一个 fibre 设备。先跑标定，标定完关掉，再启动 driver 做 0.3 的对照。

## 步骤 0.2 / 0.3 —— 关节方向与单位

### 做法

对每个关节 j1~j6，各做一次「正向小步」和「负向小步」，目视记录机械臂朝哪边动。

```bash
# 预览「关节1 增加 +0.3」
ros2 service call /calib/joint_step std_srvs/srv/Trigger \
  "{message: 'joint=1,delta=0.3'}"

# RViz 里确认后执行
ros2 service call /calib/confirm std_srvs/srv/SetBool "{data: true}"

# 如果要撤销预览
ros2 service call /calib/confirm std_srvs/srv/SetBool "{data: false}"
```

把 `joint=1` 换成 `2`~`6` 重复。

### 记录什么

对每个关节填两列：

| 关节 | 指令 +0.3 时机械臂怎么动 | 指令 -0.3 时怎么动 | URDF 里的正向是什么 |
|---|---|---|---|
| j1 | | | 绕 -z |
| j2 | | | 绕 +x |
| j3 | 绕 +x | | |
| j4 | | | 绕 +y |
| j5 | | | 绕 -x |
| j6 | | | 绕 -y |

**关键判据**：在 RViz 里看模型。如果模型转的方向和实物**相反**，说明 URDF 的轴符号与设备实际方向相反，需要在这一列记下来——阶段 1 修驱动时要按这个加负号。

### 判断单位（度还是弧度）—— 已解决，保留仅作记录

> **已确认：设备单位是度。** 本仓库早期曾怀疑是弧度，因为上游驱动把设备角度
> 直接当弧度发布，导致 RViz 里模型放大约 57 倍。实际测得
> `robot.joint_N.angle`、`robot.move_j(...)`、`robot.joint_N.set_position`
> **都是度**；URDF / MoveIt / `/joint_states` 是弧度，换算在驱动里做。
> 以下判据不必再执行。

指令 `delta=0.3` 时：

- 如果实物**只动了很小一点**（约 17°）→ 设备单位是**弧度**
- 如果实物**转了大半圈**→ 需要进一步区分

更可靠的做法：指令 `delta=1.0`，然后

- 实物转约 **57°** → 单位是**弧度**
- 实物转约 **1°**（几乎看不出）→ 单位是**度** ← **实测结果**

### 收尾：与 driver 的角度对照（0.3 后半段）

这一步需要 driver 参与，用来求「URDF 角度」与「设备原始角度」的精确换算。

```bash
# 1. 关掉标定节点（Ctrl+C），启动 driver
ros2 launch dummy_controller dummy_controller.launch.py
ros2 lifecycle set /dummy_controller configure
ros2 lifecycle set /dummy_controller activate

# 2. 重新启动标定节点（它会订阅 /joint_states）
ros2 launch dummy_vc_calibration stage0.launch.py

# 3. 对照
ros2 service call /calib/compare_driver std_srvs/srv/Trigger "{}"
```

输出形如：

```
dummy2_joint1: driver=+0.78540 device=+0.78540 diff=+0.00000
```

- `diff ≈ 0` 且数值同号 → **URDF 角度 = 设备 angle，scale=1、offset=0**，最理想
- 符号相反 → URDF 轴符号要取反
- 存在固定差值 → 那是零点偏置，记进 `offset`

### 0.4 角度范围与零点定义

用一个**手边最不心疼**的软物体（纸团）先试。归一化开口 0 = 全闭、1 = 全开，
映射到设备角度靠 `grip_angle_closed` / `grip_angle_open` 两个参数
（**当前都是占位值，需要实测修正**）。

```bash
# 先回全闭
ros2 service call /calib/gripper_step std_srvs/srv/Trigger "{message: 'open=0.0'}"
ros2 service call /calib/confirm std_srvs/srv/SetBool "{data: true}"

# 再试全开
ros2 service call /calib/gripper_step std_srvs/srv/Trigger "{message: 'open=1.0'}"
ros2 service call /calib/confirm std_srvs/srv/SetBool "{data: true}"
```

观察：

1. `open=0.0` 时两指是**完全闭合**还是**完全张开**？（如果反了，说明两端点填反了）
2. `open=1.0` 时开口有多大？用尺子量。
3. 是否有撞限位的异响？如果有，说明全开角度太大，要调小 `grip_angle_open`。

修正后写回 `config/dummy_controller.yaml`（**不要**再用 launch 参数临时覆盖，
那是调试用的）。

### 0.6 夹持力上限

⚠️ **这是最容易损坏机构的一步，务必从极小值开始。**

```bash
# 启动时就把电流上限压到很低
ros2 launch dummy_vc_calibration stage0.launch.py safe_current_limit:=0.3
```

然后用一个**有明确损坏阈值**的物体试：纸杯、鸡蛋、或卷起来的纸巾。

```bash
# 让夹爪闭合到夹住物体
ros2 service call /calib/gripper_step std_srvs/srv/Trigger "{message: 'open=0.3'}"
ros2 service call /calib/confirm std_srvs/srv/SetBool "{data: true}"
```

要记录的是**两个阈值**：

| 阈值 | 判据 | 记录值 |
|---|---|---|
| 夹稳下限 | 再小就会打滑掉落的电流值 | |
| 变形上限 | 再大就会压坏物体的电流值 | |

安全值取两者之间偏保守的一侧。**不同物体的答案不同**，Demo 阶段只用哑光方块，所以以方块的答案为准。

## 步骤 0.7 —— `set_position_with_time` 的单位

```bash
ros2 service call /calib/timed_move std_srvs/srv/Trigger \
  "{message: 'joint=1,pos=0.2,time=1.0'}"
```

节点会返回：`pos` 前后值、阻塞调用的**实际耗时**、以及你请求的 `time`。

判断规则：

| 现象 | 结论 |
|---|---|
| 阻塞耗时 ≈ 1.0 s | `time` 单位是**秒**，且是**阻塞式**的（固件走完才返回） |
| 阻塞耗时 ≈ 0.001 s，但机械臂花了 1 s 才走完 | `time` 是秒，但调用是**非阻塞**的 |
| 阻塞耗时 ≈ 1000 s（不可能，会超时） | `time` 单位是**毫秒** |
| `pos=0.2` 只转了约 11° | `pos` 单位是**弧度** |
| `pos=0.2` 几乎没动 | `pos` 单位是**度** |

这个结论直接决定阶段 3 里轨迹执行怎么写：

- 若**阻塞且单位是秒** → 直接逐点调用，天然就是正确的节拍，最理想
- 若**非阻塞** → 必须自己按 `time_from_start` 做 sleep
- 参考项目用的是 `time.sleep` + `move_j` 的笨办法，如果固件支持阻塞式，我们就能做得更好

## 步骤 0.8 —— TCP 偏移实测

目标：量出 `link7_v1_1` 末端到**两指夹持中心**的距离，写进 xacro 的 `gripper_tcp` 固定变换。

### 做法

1. 用尺子量：从 `link7` 的机械接口面，到两指**指尖前端的中点**的直线距离。
2. 拆成两个分量：
   - **沿 +y**（手指伸出方向）：`link7` → 手爪底座（URDF 里 `dummy2_hand_joint` 是 +0.052312）→ 再往前到指尖
   - **沿 x / z**：两指中心相对手爪中心有没有横向偏移

### 为什么必须实测

xacro 里现在写的是占位值 `xyz="0 0.06 0"`。这个数偏 5 mm，IK 就会把末端整体偏移 5 mm，抓取时表现为「对准了但没夹住」——而且你会先怀疑视觉，浪费大量时间在后处理上。

### 验证方法

写进 xacro 并重新 build 后：

```bash
ros2 run tf2_ros tf2_echo base_link gripper_tcp
```

手动把机械臂摆到几个已知姿态，用尺子量 `gripper_tcp` 到基座的实际距离，和 TF 报的数对比。误差应 < 5 mm。

## 附：环境编码注意事项

⚠️ 本仓库在 Windows 上编辑、在 Ubuntu 上构建，**曾因为 PowerShell 写文件时的编码往返，把源文件里的中文全部损坏成乱码**（中文被当 GBK 解读后重新按 UTF-8 写出）。

因此约定如下。注意**不是「禁止中文」**——`dummy_vc_ws/src/` 里本来就有大量
继承自上游的中文注释，它们目前完好；真正要守住的是字节级性质：

1. **一律 UTF-8，不带 BOM；换行符一律 LF。** BOM 会让 shebang 失效，CRLF 会让
   Linux 上的脚本报 `bad interpreter`。
2. **不要用 PowerShell 的 `Get-Content` / `Set-Content` 改文件**，那一趟编码往返
   就是上次事故的成因。用编辑器，或做字节级操作。
3. 改动源文件后，用自带的检查脚本验证：

```bash
python tools/check_syntax.py          # 全仓库语法检查
python tools/check_encoding.py <文件>  # UTF-8 / BOM / mojibake / 换行符检查
```

这两个脚本不依赖 ROS，Windows 和 Ubuntu 上都能跑。
